# Medley / Maiko issues found while reviving HEARTS

Issues we hit in **modern Medley Interlisp** (the Maiko VM + the macOS/SDL build) while
bringing a 1986 InterLisp-D application back to life. Recorded and shared for the
Interlisp-D community — these are candidates to report or PR upstream, not problems with
HEARTS itself. (HEARTS's own bugs live in [HEARTS-BUGS.md](HEARTS-BUGS.md).)

Environment: Medley **211029** / Maiko **211010** (Oct 2021) on macOS (Darwin 25.x, Apple Silicon),
SDL backend (`--maikoprog ldesdl`), no XQuartz. Several findings below trace to this build being
~4 years old — a current, source-matched Medley likely resolves M1/M2/M3 (see M6).

| # | Status | Issue |
|---|--------|-------|
| M1 | **root-caused** | The `CLIPBOARD` library picks `pbpaste`/`pbcopy` vs `xclip` by reading `(UNIX-GETENV "OSTYPE")` and testing for "darwin" (`library/CLIPBOARD:123-124,132-133`). `OSTYPE` is a **shell-internal, non-exported** zsh/bash var, so `getenv()` returns NULL and it *always* falls to the `xclip` branch on macOS. `run-medley` never exports `OSTYPE` either. **Two independent defects: a library bug (relies on a non-exported var; should probe for the tool, or the launcher should export the OS it already computes as `osversion`=`darwin` at `run-medley:178`) + a launcher gap.** Workaround: `export OSTYPE=darwin` before launch. *But even then it faults — see M2.* |
| M2 | **root-caused — the big one** | `(GETCLIPBOARD)` → `CREATE-PROCESS-STREAM "pbpaste"` → `FORK-UNIX` → Maiko `Unix_handlecomm` cmd 0, which talks over pipes to a **`unixcomm` helper process forked at startup**. That helper is forked **only by the `lde` kickstarter** (`ldeboot.c:111,187` `fork_Unix()`, which sets `LDEPIPEIN/OUT/STARTTIME/UNIXPID`). Launching the emulator **directly** as `--maikoprog ldesdl` (`run-medley:39,107,196`) bypasses the kickstarter, so `fork_Unix()` never runs, the `LDEPIPE*` env vars are unset, `FindUnixPipes()` fails (`unixcomm.c:248-292`), the pipe fds stay `-1`, and every cmd-0 fork `write(-1,…)`/`read(-1,…)` → returns NIL (`unixcomm.c:412-447`) → `CREATE-PROCESS-STREAM` NIL → `SETFILEINFO` on NIL faults. **Not SDL-specific and not a stub — subprocess spawning *is* fully compiled for Darwin** (`unixcomm.c` `#ifndef DOS`; `unixfork.c` has no Apple gate). It fails purely because the helper is never started. **Worse: in this 2021 build the `lde` kickstarter is X11/Sun-framebuffer only (`ldeboot.c`, `#ifdef XWINDOW`) — no SDL path — so "helper forked" and "XQuartz-free SDL" are mutually exclusive here.** Upstream fix: move `fork_Unix()` into the emulator's own `please_fork` startup so direct `ldesdl`/`ldex` launches also get the helper. Workarounds: (a) run the X11 path (`lde` + XQuartz) if you need the clipboard now; (b) **upgrade to current Medley**, where SDL is a first-class backend and this is very likely already resolved; (c) keep using file-load (`(LOAD 'X)`). |
| M3 | **root-caused (inferential)** | SEdit wedges the whole image when opened (hangs at "Select region for SEdit window"). **It's the first code to exercise an interactive press‑hold‑drag region *sweep*.** `GET-WINDOW-REGION` (`sources/SEDIT-TOPLEVEL:124`) calls `IL:GETREGION` → `\MEDW.GETSCREENREGION` (`HLDISPLAY:1016`) → `\GETREGIONTRACKWITHBOX` — a **non-yielding spin loop with no `(BLOCK)`** (`HLDISPLAY:601`, sweep at `:1119`) that must see a button *held across motion* then *released*. The game's working mouse instead uses `\TRACKWITHBOX` (`HLDISPLAY:747`) — a discrete *click-to-place*, which is why "the game reads the mouse fine" doesn't clear this path. Under X11, `xwinman.c:192-234` maintains the held-button bit across `MotionNotify` **and** forces a reschedule kick (`Irq_Stk_End = Irq_Stk_Check = 0`) on button events; the SDL event driver evidently doesn't, so the sweep's terminating transition is never observed and the non-yielding spin monopolizes the single-threaded VM → total wedge (worsened because the wait holds the SEDIT context monitor lock, `SEDIT-BASE:901`, inside a spawned process). **Report to Maiko's SDL display/event driver, not SEdit.** Confirm cheaply: while wedged, one host CPU core at ~100% ⇒ the non-yielding spin. Workarounds: pre-seed the `REGIONS` stack so `GETREGION` is skipped (`lispusers/TILED-SEDIT`, `LAYOUT-SEDIT` place SEdit windows programmatically); use the X11 `lde`/`ldex` backend for editing; or upgrade Medley. |
| M6 | note (blocks full proof) | **The bundled Maiko source tree `maiko-maiko-211010` (Oct 2021) contains no SDL code at all** — no `sdl*.c`, no `SDL_*` refs; its makefiles build only `lde`/`ldex` and its README says X11-only. So the running `ldesdl` binary was built from a **newer Maiko than the sources in this install**. The Lisp-side asymmetry behind M3 is proven from these sources, but the decisive SDL C defect lives in code not present here — reading the actual `ldesdl` Maiko source (its `SDL_MOUSEMOTION`/`MOUSEBUTTON` handling vs `xwinman.c:192-234`) would turn M3 from strongly-suggestive into proven. Another reason to move to a current, source-matched Medley. |
| M4 | note | `--vnc` headless display is explicitly unavailable on macOS; SDL (`--maikoprog ldesdl`) is the no-XQuartz path but needs `SDL2.framework` + an `install_name_tool` rpath fix + an ad-hoc re-sign (DYLD_* is stripped through `/bin/bash`). Documenting the exact recipe would help other macOS users. |
| M5 | note (not a bug) | `INVERTREGION` exists in Medley's sources (`TWODINSPECTOR`) but is **not loaded** in the apps sysout, so calling it faults. Use core `(DSPFILL region BLACKSHADE 'INVERT dsp)` instead. A good reminder that "in the sources" ≠ "in the running image". |
